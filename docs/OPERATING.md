# Operating Proofgen at a show — guide for an agent helping the photographer

You are most likely reading this because the photographer asked you (Claude Code
or another agent, in a terminal on his Mac) to help him get photos through
Proofgen: "handle the pending classes", "why aren't my proofs online", "I forgot
how this works". This is what the system does, what matters, and what to run.

He is shooting a live horse show. He has minutes between classes, often none.
**Do the routine work for him, tell him in one or two plain sentences what you
did, and ask only when the answer changes what happens to his photos.** No jargon:
say "the background workers", not "Horizon"; "the website", not "Gallery".

## What matters, in order

1. **Never lose a photo.** Originals are irreplaceable. Nothing you do may delete,
   move, overwrite, "clean up" or re-number photos on your own initiative. When
   unsure, stop and ask. A card is only emptied by the Card Reader, and only after
   two verified copies exist.
2. **Proofs online fast.** Customers order from the proofs on the website, often
   while the class is still leaving the ring. Proofs beat everything else.
3. **Never get in the way of ordering.** Do not rename, renumber or re-upload
   things that are already on the website without asking: proof numbers are what
   customers order by.
4. **Web and high-res images can wait.** They drip up behind the proofs.
5. **Do not fix Proofgen's code here.** Never edit tracked files, commit, reset or
   "clean" the checkout. Work around the problem, then **file a report** (below)
   so the developer fixes it properly.

## How it works

```
camera card ──Card Reader──▶ class folder  ──Import──▶ photo in the catalog ──▶ proofs, web, high-res ──Upload──▶ website
                    └──────▶ archive drive (second copy)        (renamed to a proof number)   (generated by the workers)
```

- **Show** = one event, a folder named like `26AAC` in the working folder. Shows
  are **created on the website first**, then picked in Proofgen (Create Show).
- **Class** = one folder inside the show (`005`, `012-A`). The folder name is the
  class number on the website: letters, numbers, `.`, `-`, `_`; must start and
  end with a letter or number; 32 characters at most. No spaces.
- **Import** takes the JPEGs sitting in a class folder, gives each a proof number
  (`26AAC_00042`), moves the original to `originals/`, and writes a second copy to
  the archive drive when Backups are on. The same photo is never imported twice:
  it is recognized by its content.
- **Generation** (automatic after import): two proof sizes with the watermark, a
  web image, a high-res image. Done by the background workers.
- **Upload**: proofs first for every class, then web, then high-res one at a time.
  With "Uploads: On" in the header it happens by itself as each kind finishes.
- **Process** (the button on the show page, next to the Card Reader): one press
  queues everything that is waiting for the show — imports, then generation,
  then uploads — and tells you in one sentence what it did and what it skipped.
  It works even while other work is already queued, so it is also the way to
  restart anything that stopped moving. The background workers do the rest.
- The **background workers** do all of this. If they are stopped, nothing moves.
  They are started and stopped from the header of any Proofgen page.

## The commands

Run them from the Proofgen folder. `herd php` makes sure the right PHP is used.

```sh
herd php artisan proofgen:status                 # is everything running? which shows exist?
herd php artisan proofgen:status 26AAC           # every class: what is waiting, and the next step
herd php artisan proofgen:status 26AAC --website # also confirm the show exists on the website
herd php artisan proofgen:process 26AAC          # queue everything pending, in one go (same as the Process button)
herd php artisan proofgen:process 26AAC --json   # the same, machine-readable
herd php artisan proofgen:import 26AAC --all     # queue every class that has photos waiting
herd php artisan proofgen:import 26AAC 005       # one class
herd php artisan proofgen:upload 26AAC --all     # queue every class with something to upload
herd php artisan proofgen:upload 26AAC --all --proofs-only
```

`status` is read-only and safe at any time; add `--json` to parse it. `process`
(and the Process button) are safe to repeat and skip, with an explanation, what
they cannot do: folders whose name the website would reject, imports without
the archive drive, and uploads to a show that is not on the website yet.
`import` and `upload` do exactly what those two buttons do when you want to
touch only one stage or one class.

## "Handle all the pending classes"

1. `herd php artisan proofgen:status <show>`. Read the health lines first.
   - Workers stopped → ask him to press the start button in the page header (or
     tell him you cannot continue until they run). Do not start them another way.
   - "ON BUT DRIVE MISSING" → the archive drive is unplugged; imports will fail.
     Ask him to plug it in. Do not turn Backups off for him.
   - A working-folder warning about iCloud → tell him; do not move folders.
2. Then run `herd php artisan proofgen:process <show>`. One pass queues every
   class that has photos waiting, generation for every imported photo, and
   uploads for everything generated but not on the website — what the Import,
   generate and Upload buttons would have done, without waiting for any of it
   to finish. It prints one sentence about what it queued and what it skipped
   (the background workers stopped, a folder to rename, uploads without a
   destination, photos that need review). The Process button on the show page
   does the same thing.
3. Handle what only he can do, from the status table:
   - `rename the folder` → tell him the problem and the suggested name from the
     status output. He renames it on the show page (the red class row). Never
     rename folders on disk yourself: a class that already has photos must be
     renamed through the app so the records move with it.
   - `review issues` → the Issues page in the app. Issues are usually a photo that
     is already in another class (same content). Describe them; let him choose.
4. Run `status` again and tell him, briefly: what is online, what is still going.

## Dumping cards

Show page → **Card Reader**. He puts a card in, picks the class (or "Split into
multiple classes" when a card holds several), presses Copy. Two verified copies are
made; the import starts by itself; with "Empty the card" on, the card is emptied of
exactly the photos that were verified. **An empty card means it was safely dumped.
A card that still has photos means: stop, do not shoot over it, look.**

If the Card Reader says macOS is blocking the card: System Settings → Privacy &
Security → Full Disk Access → turn on **Herd**, then restart the background workers
(Settings → Card access explains this and shows whether it is working). You cannot
grant this for him.

Without the Card Reader, copying JPEGs into the class folder by hand works too:
they show up as "to import".

## When something is wrong

| What he sees | Check | Usually |
| --- | --- | --- |
| Nothing is happening | `status`: workers stopped? | He starts them from the page header |
| Nothing is queued or running, but photos still need generating | `status` says so under the table | Run: `proofgen:process <show>` (or press Process on the show page) |
| Photos imported but no proofs | `status`: "to generate" not moving | Workers stopped, or the queue is long; wait, then restart workers from the header. `proofgen:process <show>` queues whatever generation is still missing |
| Proofs made but not on the website | `status`: "to upload" > 0; is "Uploads" Off in the header? | `proofgen:process <show>` or `proofgen:upload <show> --all`; bad wifi makes it slow, not broken |
| Upload fails for one class | the log (below) names the request and field | Folder name the website rejects → rename in the app. "Create it on the website first" → the show does not exist on the website yet |
| "Destination changed" on the show page | the panel shows old and new | Do **not** accept it for him; ask the developer unless he knows the website moved |
| Import fails | `status`: archive drive missing? | Plug the drive in, import again. Already-imported photos are skipped, numbers are not wasted |
| A strip says the disk is low, or "second copies" are using space | the top bar | Pressing **Free … GB** is safe: it removes only camera files whose imported photo (and backup) was checked first. Do not delete anything by hand |
| Every page errors | `herd php artisan proofgen:status` still works? | Read the last log lines; file a report |
| A card will not read | Settings → Card access | Herd needs Full Disk Access |

The log: `tail -n 60 storage/logs/laravel.log`. Failed jobs:
`herd php artisan queue:failed | tail -20`. Retrying is safe for imports, generation
and uploads: `herd php artisan queue:retry all`. **Never** `queue:flush`,
`queue:clear`, `migrate:fresh`, `horizon:clear`, or delete files to "unstick" it.

**Stuck** (workers running, numbers not moving for minutes): read the log tail, ask
him to press the restart-workers button in the header, check again. If it is still
stuck, file a report with severity `blocking` and tell him plainly that you could
not fix it and the developer has been told.

## Updating Proofgen

When a new version exists a blue bar appears at the top of every page with
**Update now**, **Remind me later** (asks again in 4 hours) and **Skip this
version**. Update only when he or the developer asks, and between classes, not
during an import: press **Update now** on the bar, or Settings → Services → Update. If
that fails, stop and report; do not improvise `git` commands. Upgrading a very old
install is a different, supervised job: `docs/UPGRADE_FROM_V1.md`.

## Telling the developer

Anything that looks like a bug, a confusing screen, a wrong instruction in this
guide, or something you had to work around:

```sh
herd php artisan proofgen:report --llm --filed-by "Claude Code session with <name>" \
  --severity <low|normal|high|blocking> --title "<one line>" \
  --what "<what you saw and ran>" --expected "<what should have happened>" --suggestion "<idea>"
```

It attaches the system's state, removes secrets, and reaches the developer even if
the wifi is down right now (it is sent later). Tell him you filed it. Details:
`docs/FEEDBACK.md`. Deeper reference when you need it: `docs/photo-pipeline.md`
(import and upload internals), `docs/CARD_READER.md`.
